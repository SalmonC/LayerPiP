## 3. 高能进度条：可以采纳什么

1. **F1 与 F2 分离**。没有官方曲线也能记录已看区间；获取曲线失败不应阻止拖动和播放。
2. **请求路径与 `r=loader`**。官方脚本确实向 `bvc.bilivideo.com/pbp/data` 请求，追加该参数并关闭凭证。旧文档的 404 不足以得出接口下线结论。
3. **归一化、曲线面积、已看裁剪分层**。报告的补零、1000×100 viewBox、20% 基底、三次贝塞尔和区间矩形，与已取得的官方脚本基本一致。保留数值校验、至少两点的前提。
4. **按身份缓存及代次守卫**。报告借鉴字幕 manager 的做法合理；远端响应不能写回已换 CID 的界面。
5. **纯渲染层不负责请求或存储**。曲线路径随数据变更计算，播放过程中只更新必要位置，避免把网络、持久化和每帧渲染混在组件里。
6. **不造假曲线**。无曲线保持 F1；不把本地近似当成官方曲线。本地近似不是首版必要能力。

报告称它为弹幕密度曲线，适合作为产品解释；返回值的具体权重和服务端聚合算法并未被本次核查证明，不能把每个样本值直接解释成“这一秒有多少条弹幕”，也不能解释成 AI 精彩度或观看次数。

## 4. 高能方案必须修订的地方

### 4.1 已看采集伪代码不能照搬

报告第 4.1 节定义 `ratio = currentTime / duration`，随后却拿比例差与“1.5 秒”比较。对于 1000 秒视频，从 100 秒跳到 500 秒，比例差只有 0.4，条件不会识别这个大跳转。

`lastUpdateTime - ratio >= 15` 在向前播放时也不会成立。已取得的官方脚本确实存在类似的反向减法，但官方实现存在缺陷不构成复刻缺陷的理由。此外，周期落盘要有独立的上次落盘时间；仅把减法反过来，若每次采样都更新 lastUpdateTime，仍不能实现每 15 秒落盘。

另一个独立风险：`onSeeking()` 发生时 `currentTime` 可能已经是目的时间；此时 `commit()` 若读取目的时间作为段尾，就会把整个跳过区间误记为已看。结算只能使用最后一个有效播放样本或浏览器提供的已播放区间。

**建议采用的语义：**

- 持久化及采集使用秒数，渲染时才除以有效 duration；字段明确叫 `startSec/endSec`，避免混淆。
- 首选评估 `HTMLMediaElement.played` 作为当前媒体实际播放区间来源，再与持久化数据求并集。它已有“播放过哪些区间”的语义，比凭时间变化猜测 seek 更贴合目标。[HTML 媒体规范](https://html.spec.whatwg.org/multipage/media.html#dom-media-played)
- 使用 played 仍须绑定媒体对象与视频身份：同一元素换源/CID 时切换所属记录；换 P 期间无法确认归属的样本不写入。读取是快照，必要时重新读取。
- 若兼容性原因需要自建采样，区分媒体秒、单调时钟、播放速率和 seeking 状态；暂停、等待缓冲不扩展区间。倍速和后台事件稀疏不能机械套用 1.5 秒阈值。
- 首帧只设起点，后续确认播放才扩展；跳转先结束旧段，seeked 后重新设起点。
- 使用独立的墙钟节流保存脏数据，在 pause/身份切换/关闭时补充提交。关闭时提交只做最后补救，不能依赖异步 unload 写入必然完成。

这里的“已看”建议明确定义为“媒体实际播放过”，不是证明用户目光停留。多画面中的静音视频是否计入、是否包含打开小窗前原网页已播放的区间，是产品语义，不能由 isActive 或静音状态暗中决定。

### 4.2 不能继续让蓝色前缀覆盖全部过去时间

0.2.14 的主轨道仍是标准“当前位置前全部蓝色”的播放进度；这与“已看区间可以不连续”的新目标不同。

若从 00:30 跳到 08:00，当前蓝色前缀会把 00:30–08:00 全染蓝。新增 watched 覆盖层放在下面无效，放上面若没有遮掉原前缀仍会误导。

建议三层关系：灰白基础轨道、半透明缓冲层、已看蓝色区间；当前位置以滑块/时间标记表示。存在高能数据时，同一已看集合再用于曲线裁剪。底部 2px 常驻线采用同一语义，避免控制栏显隐时蓝色含义变化。先确定这一规则，再谈叠层样式。

### 4.3 API 契约需要适配原生 fetch

报告例子 JSON 顶层为 `modules`；其 `parse()` 却读取 `res.data.modules`。后者是官方 HTTP 客户端的响应包装，不是 `fetch(...).json()` 的返回体。照着“内容脚本直接 fetch + 原样 parse”接线，会将有效结果误判为空。

应明确：传入 JSON body，读取 body.modules；若复用带包装的网络层，在边界处解包一次。`step_sec` 要检查为有限正数，而不是仅做 truthy 判断；points 校验为有界数组、有限非负数。不能执行返回的 `script_src`，它仅是上游元信息。

将“正常无曲线”与“412/网络错误/非法响应”区分为内部状态。两者都可让用户继续看视频，但缓存策略不同：暂时错误不能永久缓存为无数据，也不能每帧重试。CORS 星号允许无凭证读取的方向合理，但不保证风控和实际扩展运行环境永远放行。

### 4.4 官方历史只作可选导入

采纳不写官方 `pbp3` 的原则；首版完全可以只用扩展记录，减少站点数据库依赖。

若导入官方记录：

- 先探测库并不完全消除创建竞态。探测后数据库可能被删除；打开触发 `onupgradeneeded` 时应中止升级事务，不能仅仅“不建表”。检查 store 是否存在，使用 readonly transaction。
- 校验 CID、到期时间、数值、区间顺序及范围，再求并集；兼容 expire/expireTime 不等于任意字段都可信。
- `last_play_time` 只能表示上次位置，不能生成 `[0,last_play_time]` 的已看区间。报告第 4.3 节把它列入“三路并集”容易与其后面的提醒冲突，应从区间来源中移除，可另作位置标记。

### 4.5 持久化需要真正的设计

`src/background/subtitleAssets.ts` 目前数据库版本是 1，仅有 `subtitle-assets` store。“沿用库模式”不能直接变成在版本 1 中添加新 store。可选择独立的扩展观看记录库以减少对字幕资产的影响；若共库，应设计升级和旧版本兼容，实施时走项目的数据变更规则。

无论选哪一种，合并写入由 background 统一处理，使用事务完成作为成功依据，避免两路/两标签同时写同一 CID 时后写覆盖先写。现有字幕资产函数在 request.onsuccess 就返回的写法，不宜直接复制为新功能的持久化模板。

还需明确记录寿命、清除入口、最大体积、相邻合并容差、重复上报幂等性、duration 变化和过期回收。布局记录与观看区间不应混成一种数据。

### 4.6 接线和配置缩小范围

报告中的 `top:-8px/16px/--offset:38px` 等属于旧源码；当前是稳定的 20px 命中区、4px 轨道、12px 两侧留白及独立底部细线，不能按旧“轨道移形”规则实现。

纯 SVG 应明确 clip ID 每实例唯一，兼容未来多 pane；避免负 z-index 进入父级背景后面。整体保持 pointer-events:none，不改变现有 seek 命中区。

首版建议只保留“显示已看区间”和“显示高能曲线”两个概念。颜色跟随蓝色主题，透明度和高度先采用已确认规格；不提前加入颜色选择、本地近似、多层总开关等尚无必要的选项。长数组降采样应保留时间位置和峰值，不以任意抽点冒充原曲线；对拍关注归一化和几何结果，不把 SVG 空格差异当成产品错误。

## 5. 多画面：可以采纳什么

- 单个 Document PiP 容纳多个 iframe 的路线有规范依据。[Document PiP 规范 §3.3](https://wicg.github.io/document-picture-in-picture/#iframes)
- 在目标 PiP document 中创建 iframe，避免搬动已加载 frame 带来的重载问题。
- 先做两路，上限与资源控制明确；四路、分隔条、布局持久化、多路 AI 均后置。
- 每个 pane 稳定身份、播放状态独立；activePane 与 audiblePane 分开。
- 关闭必须销毁会话、监听和 frame，不能只是隐藏界面。
- 复用现有窗口生命周期经验合理；但不是在现有 body 中追加两个 frame 就完成复用。

完整 B 站页面可以复用站点播放器，但登录、清晰度、原生字幕可用性仍受账号、视频和环境影响。不能把“免费具备全部功能”当成承诺。

## 6. 多画面方案必须修订的地方

### 6.1 从“能播放”到“插件会话”之间仍缺一层

`DocPIPWebProvider.onOpenPlayer()` 目前先初始化单路 HtmlVideoPlayer，再将它的 playerRootEl 挂入 PiP，并绑定窗口销毁。报告让 pane[0] 再加载一次当前视频，会产生另一个媒体实例。若旧单路实例和网页原视频继续播放，会有重复音频、额外解码、两个播放位置以及关闭恢复歧义。

推荐先定义窗口会话所有者，再决定当前视频怎样进入多画面：

- 方案 A：保留现有当前视频作为主 pane，新增 iframe 为第二 pane。优势是原视频、字幕绑定和播放位置连续；代价是两种 pane 适配器并存。
- 方案 B：两路全部 iframe。控制模型统一，但要暂停并保留原视频，传递当前时间与播放意图，退出时只向明确的原始目标恢复状态。

这两条都可评估。本轮不武断决定 A 或 B；报告默认 B，却没有写完 B 的交接事务。至少应设计“单路→多路”“失败退回单路”“退出多路→恢复主路”“关闭整个小窗”四条路径。

### 6.2 all_frames 不等于所有业务自然可用

当前源码证据：

- `entry-all-frames.prod.ts` 在各 frame 加载 main.js；但 `src/contents/main.ts` 只有 isTop 才运行主逻辑，子 frame 主要响应视频检测。
- `main.ts` 顶层仍导入 floatButton，可能有注入副作用。
- all-frame MAIN 入口会加载 injectPIPFunction/fetchHacker。
- nativeMediaSession 的安装在 top-only 入口；B 站自身的 Media Session 行为又是另一层。

因此必须分别处理“阻止现有副作用”和“接入需要的 pane 控制”，不能把 iframe 的 isTop 改为 true 来启动整套主逻辑。需要独立、受限的 pane 适配入口，早于相关副作用安装。[Chrome 内容脚本说明](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts#specify-frames)

### 6.3 pane 标识不能靠共享站点状态兜底

window.name 可作为发现提示，不宜作为唯一授权依据。建议由宿主保存 frame→pane 映射，通过限定 origin、source、paneId、会话代次的握手确认，并在导航后重新绑定。跨源跳出目标视频页时应进入不可控/失败状态，而不是继续把命令发给旧对象。

报告建议写 sessionStorage，与“不写站点存储”原则直接冲突；同源、同一顶层上下文的 frame 还可能共享这份存储，通用标志会串 pane。[HTML Web Storage 规范](https://html.spec.whatwg.org/multipage/webstorage.html)

### 6.4 音频规则是产品选择，不能写成浏览器绝对限制

“默认静音、最多一路出声”值得采用；“两路不可能同时出声”不能由一次匿名自动播放实验推出。Chrome 自动播放受用户互动、权限委派和媒体参与度等因素影响，同源 frame 的权限情况也不同。[Chrome 自动播放策略](https://developer.chrome.com/blog/autoplay/)

宿主点独奏时，先静音旧路，再尝试目标解除静音/播放；以真实 muted、paused 和 play() 结果更新 UI。被拒绝时提供进入目标 pane 点击播放的路径，不能仅把 soloed 设为 true。

保留 B 站原生音量控件时还须监听其 volumechange，处理用户在另一 pane 手动开声；否则“唯一有声”约束很快失效。需要区分本站自身保存音量偏好和宿主临时静音，避免多个同源页面的偏好同步反复覆盖宿主决定。

### 6.5 两路并播、焦点和系统媒体控制要一致

报告的“非激活 pane 默认暂停”与目标相冲突。建议默认两路持续播放、只有选定一路有声；“只播放激活画面”是可选省资源模式，焦点变化不能偷偷暂停另一路。

键盘事件不会像同一 DOM 树那样从子文档冒泡到父文档。宿主应有每个 pane 的事件适配和唯一命令路由，保留输入框保护；宿主按钮作用于 activePane，pane 内按键由明确的一方处理。不要同时让 B 站与 LayerPiP 各处理一次空格。

禁用插件自己的 Media Session 不等于禁用了 B 站页面注册的 handler。应审查站点层和扩展层的所有权，并以实际系统媒体键目标为验收项。纯 UI 选中态不能证明系统路由正确。

### 6.6 原生页布局不是可有可无的后期优化

将整页放进半宽 iframe，可能出现导航、推荐、评论和极小播放器。为 pane 限定播放器可见区域和尺寸是两路最小版本的必要条件。需要等待原生播放器就绪、处理站点重建 DOM、恢复/关闭，不能只依赖一次隐藏非播放器节点。

320px/480px 纵向堆叠只是候选，不能保证可用：还要依据窗口高度、视频宽高比和最小可操作控件尺寸选择布局。允许某一路放大查看比强制四格更重要。

### 6.7 将安全接线前置到 P0

受限 pane、默认静音、禁止递归开窗、基本焦点归属、加载失败关闭和原视频交接必须与双路演示同时具备，不应等 P1。P0 出口应为“当前插件能打开、能控制、能安全退出的两路窗口”，不只是两条 currentTime 在前进。

iframe.allow='autoplay; fullscreen' 不会取消 PiP 的 fullscreen 限制；无实际能力的入口应隐藏或改成 pane 内放大，而不是显示一个必然失败的全屏按钮。[Document PiP 规范 §3.2.4](https://wicg.github.io/document-picture-in-picture/#fullscreen)

## 7. 不采纳报告中的绝对化表述

| 原结论倾向 | 本次结论 |
| --- | --- |
| 全浏览器进程单槽位是规范恒定事实 | 规范要求每个 opener 最多一个；跨顶层窗口是否只允许一个由实现和平台决定。当前产品可按目标 Edge 限制设计，但不扩大成所有浏览器永久结论。[规范 §6.5](https://wicg.github.io/document-picture-in-picture/#one-pip-window) |
| 嵌入播放器 9 秒没加载就不适合 | 足以降低优先级，不足以证明不可行；且 all_frames 匹配范围包含其 URL，不能简单断言没有本扩展注入。跨源 DOM 控制不同，仍需适配 |
| 直接流播放只能靠 DNR | 当前样本的 Referer/CDN 失败是风险证据，不证明所有取流方式都必须 DNR；DASH 音视频拆分、MSE、鉴权和清晰度同样是工程问题。首版不选该路线合理 |
| 其他标签页 DOM 绝对不可访问 | 无窗口引用的普通标签不能直接借用 DOM，是实际限制；有 opener 引用且同源的情形不同。不建议首版依赖跨标签 DOM，不等于平台上任何情形都不可能 |
| 逐字符串对拍、完整测试清单照单执行 | 只保留能检测明确风险的检查，遵守用户不做无谓单元测试的要求。键盘所有权确有修改时仍执行项目强制回归 |

## 8. 后续实施前需要冻结的决策

不需要再次讨论的大方向：一个 PiP 内两路、每路独立控制、已看区间与高能曲线独立、无数据不造曲线、主题采用用户确认的蓝色。

需要明确但本轮不要求用户逐条即时回答：

1. 多画面的当前视频是保留原媒体还是重载到 iframe；退出时恢复哪个视频及哪个时间。
2. 已看是否包含原网页播放、静音播放及非激活 pane；建议默认按实际播放统计，并提供清除记录。
3. 最多一路出声是默认还是硬约束；建议首版作明确约束，UI 区分焦点路与有声路。
4. 两项功能的产品优先级；建议先交付改动范围较小的 F1/F2，再独立推进多画面。

未来验证应围绕少量反例：跳过大片段不染蓝、回看求并集、倍速/暂停不误记、切 CID 不串数据、两路同 CID 不丢写、接口风控下退化、只一路有声、关闭后无残留播放。浏览器实机由用户协助，不自动展开长期实验或全面测试工程。

## 9. 本轮结论

两份报告可以作为有效研究输入。高能曲线的上游路径与几何算法可复用，已看区间的状态与持久化方案必须修订；多画面保留 iframe 候选路线，但先补会话交接与 pane 控制协议，不能按当前 P0/P1 划分直接开工。本轮没有开始实施。
